1. はじめに

1.1. 導入（Getting Started）

本書の目的は、対話型定理証明支援系「Lean 4」を使用して数学を形式化する方法を学ぶことです。前提として、ある程度の数学的知識を仮定していますが、それほど高度なものは必要ありません。数論から測度論、解析学に至るまで幅広い例を取り上げますが、それらの分野の初歩的な側面に焦点を当てているため、もし馴染みのない内容であっても、学習を進めながら身につけていくことができるでしょう。また、形式手法に関する事前の知識も一切仮定していません。形式化とは、一種のプログラミングのようなものだと考えることができます。私たちは、Leanが理解できるような規則正しい言語（プログラミング言語のようなもの）で数学的な定義、定理、証明を記述します。その見返りとして、Leanはフィードバックや情報を提供し、式を解釈してそれが整形式（well-formed）であることを保証し、最終的に私たちの証明の正しさを保証してくれます。

Leanについての詳細は、LeanプロジェクトのページやLeanコミュニティのウェブページをご覧ください。本チュートリアルは、Leanの巨大かつ常に成長し続けているライブラリ「Mathlib」に基づいています。また、まだ参加していない方は、Lean Zulipオンラインチャットグループに参加することを強くお勧めします。そこには、質問に喜んで答え、精神的にサポートしてくれる、活気に満ちた温かいLean愛好家のコミュニティがあります。

本書のPDF版やHTML版をオンラインで読むことも可能ですが、VS Codeエディタ内からLeanを実行しながら、対話的に読み進めるように設計されています。始めるには：

  1. 以下のインストール手順に従って、Lean 4とVS Codeをインストールします。
  2. VS Codeの右上隅にある「forall（∀）」記号をクリックし、「Open Project」、「Download Project」、「Mathematics in Lean」の順に選択してリポジトリを取得します。
  3. 本書の各セクションには、例と演習問題を含む対応するLeanファイルが用意されています。これらは章ごとに整理された MIL フォルダ内にあります。そのフォルダのコピーを作成し、そのコピーの中で実験したり演習問題を解いたりすることを強くお勧めします。これにより元のファイルがそのまま保たれ、リポジトリが変更された際に行う更新も容易になります（下記参照）。コピーの名前は my_files など好きなものにして構いませんし、自分自身のLeanファイルを作成するためにも使用できます。

その上で、VS Codeのサイドパネルで教科書を開くには、次のように操作します：

  1. ctrl-shift-P （macOSの場合は command-shift-P）を押します。
  2. 表示されるバーに Lean 4: Docs: Show Documentation Resources と入力し、リターンキーを押します（メニュー内でハイライトされたらすぐにリターンキーを押して選択できます）。
  3. 開いたウィンドウで Mathematics in Lean をクリックします。

あるいは、Codespacesを使用して、クラウド上でLeanとVS Codeを実行することもできます。その方法についての詳細は、Github上の Mathematics in Lean プロジェクトページに記載されています。なお、前述したように、MIL フォルダのコピー内で作業することをお勧めします。

この教科書と関連リポジトリは現在も制作途中のものです。リポジトリを更新するには、mathematics_in_lean フォルダ内で git pull に続けて lake exe cache get と入力します（これは MIL フォルダの内容を変更していないことを前提としています。コピーの作成を勧めたのはそのためです）。

本書では、解説、指示、ヒントが含まれる教科書を読みながら、MIL フォルダ内の演習問題に取り組むことを想定しています。本文には、以下のような例が頻繁に登場します：

#eval "Hello, World!"

対応するLeanファイル内で該当箇所を見つけることができるはずです。その行をクリックすると、VS Codeの「Lean InfoView」ウィンドウにLeanからのフィードバックが表示され、カーソルを #eval コマンドの上に合わせると、ポップアップウィンドウにこのコマンドに対するLeanの応答が表示されます。ファイルを編集して、ご自身の例を試してみることをお勧めします。

さらに本書には、挑戦しがいのある演習問題がたくさん用意されています。これらを急いで飛ばしてしまわないようにしましょう！ Leanの本質は、ただ読むことではなく、対話的に数学を「実践する」ことにあります。演習問題を解き進めることは、その体験の中心となります。すべてを解く必要はありません。関連するスキルをマスターしたと感じたら、自由に先に進んで構いません。自分の解答は、各セクションに関連付けられた solutions フォルダ内の解答といつでも比較することができます。

1.2. 概要（Overview）

簡単に言えば、Leanは「依存型理論（dependent type theory）」として知られる形式言語で複雑な式を構築するためのツールです。

すべての式には型（type）があり、#check コマンドを使用することでそれを表示させることができます。一部の式は ℕ や ℕ → ℕ のような型を持ちます。これらは数学的対象です。

#check 2 + 2
def f (x : ℕ) := x + 3
#check f

一部の式は Prop 型を持ちます。これらは数学的命題です。

#check 2 + 2 = 4
def FermatLastTheorem := ∀ x y z n : ℕ, n > 2 ∧ x * y * z ≠ 0 → x ^ n + y ^ n ≠ z ^ n
#check FermatLastTheorem

一部の式は型 P を持ち、その P 自身が Prop 型を持ちます。そのような式は、命題 P の証明となります。

theorem easy : 2 + 2 = 4 := rfl
#check easy
theorem hard : FermatLastTheorem := sorry
#check hard

もしあなたが FermatLastTheorem 型の式を何とか構築し、Leanがそれをその型の項として受け入れたならば、それは非常に素晴らしい成果です（sorry を使うのはズルであり、Leanはそれを知っています）。これでゲームのルールは分かりました。あとはルールを学ぶだけです。

本書は、姉妹編のチュートリアルである『Theorem Proving in Lean』（Leanでの定理証明）を補完するものです。同書では、背後にある論理的枠組みやLeanのコアな構文について、より徹底的な入門を提供しています。『Theorem Proving in Lean』は、新しい食洗機を使う前に、取扱説明書を最初から最後まで読みたい人のためのものです。もしあなたが、とりあえず「スタート」ボタンを押して、ポットスクラバー機能の有効化はそのあとで考えたいタイプの人であれば、本書から始めて、必要に応じて『Theorem Proving in Lean』を参照する方が理にかなっているでしょう。

『Mathematics in Lean』が『Theorem Proving in Lean』と異なるもう一つの点は、本書ではタクティク（tactics）の使用に遥かに重点を置いていることです。複雑な式を構築しようとする際、Leanには2つのアプローチがあります。式そのものを書き下す（つまり、その適切なテキスト表現を記述する）か、あるいは式をどのように構築すべきかについての指示（instructions）をLeanに与えるかです。例えば、次の式は、「n が偶数ならば m * n も偶数である」という事実の証明を表しています：

example : ∀ m n : Nat, Even n → Even (m * n) := fun m n ⟨k, (hk : n = k + k)⟩ ↦
  have hmn : m * n = m * k + m * k := by rw [hk, mul_add]
  show ∃ l, m * n = l + l from ⟨_, hmn⟩

この証明項（proof term）は、1行に圧縮することができます：

example : ∀ m n : Nat, Even n → Even (m * n) :=
  fun m n ⟨k, hk⟩ ↦ ⟨m * k, by rw [hk, mul_add]⟩

一方、次のコードは同じ定理のタクティクスタイル（tactic-style）の証明です。-- で始まる行はコメントであるため、Leanからは無視されます：

example : ∀ m n : Nat, Even n → Even (m * n) := by
  -- m と n を自然数とし、n = 2 * k と仮定する。
  rintro m n ⟨k, hk⟩
  -- m * n が自然数の2倍であることを証明する必要がある。m * k の2倍であることを示そう。
  use m * k
  -- n を代入し、
  rw [hk]
  -- これで明らかになる。
  ring

VS Codeでこのような証明の各行を入力していくと、Leanは別のウィンドウに証明の状態（proof state）を表示し、すでに確立した事実と、定理を証明するために残っているタスクを教えてくれます。カーソルがある時点での証明の状態をLeanが常時表示してくれるため、行をステップ実行しながら証明を再現することができます。この例では、証明の最初の行が m と n を導入し（必要であればその時点で名前を変更することもできました）、さらに仮説 Even n を k と n = 2 * k という仮定に分解していることがわかります。2行目の use m * k は、m * n = 2 * (m * k) を示すことによって m * n が偶数であることを示すという宣言です。次の行では rw タクティクを使用してゴール内の n を 2 * k に置き換え（rw は "rewrite" の略）、最後の ring タクティクによって得られたゴール m * (2 * k) = 2 * (m * k) を解きます。

小さなステップとインクリメンタルなフィードバックを受け取りながら証明を構築できる能力は、非常に強力です。そのため、タクティクによる証明は、多くの場合、証明項を書くよりも簡単で迅速に行えます。両者の間に厳密な境界線があるわけではなく、上記の例の by rw [hk, mul_add] のように、証明項の中にタクティクを挿入することもできます。同様に、タクティク証明の途中に短い証明項を挿入することが役立つ場合も多々あります。とはいえ、本書ではタクティクの使用に重点を置きます。

上の例では、タクティク証明も1行にまとめることができます：

example : ∀ m n : Nat, Even n → Even (m * n) := by
  rintro m n ⟨k, hk⟩; use m * k; rw [hk]; ring

ここでは小さな証明ステップを実行するためにタクティクを使用しました。しかし、タクティクは高度な自動化を提供し、より長大な計算や大規模な推論ステップを正当化することもできます。例えば、パリティに関する命題を自動的に証明するための特定の規則を持ったLeanのシンプリファイア（simplifier）を呼び出すことができます。

example : ∀ m n : Nat, Even n → Even (m * n) := by
  intros; simp [*, parity_simps]

2つの導入部のもう一つの大きな違いは、『Theorem Proving in Lean』がコアとなるLeanと組み込みのタクティクのみに依存しているのに対し、『Mathematics in Lean』はLeanの強力かつ常に成長し続けているライブラリ「Mathlib」の上に構築されている点です。その結果、ライブラリに含まれる数学的対象や定理の使い方、そして非常に便利なタクティクのいくつかを紹介することができます。本書はライブラリの完全な概要として使用されることを意図したものではなく、詳細なドキュメントはコミュニティのウェブページに掲載されています。むしろ私たちの目的は、その形式化の根底にある思考様式を紹介し、ライブラリをブラウジングして自分で物事を見つけやすくなるように基本的なエントリーポイントを示すことです。

対話型定理証明はフラストレーションが溜まることもあり、学習曲線は急峻です。しかし、Leanコミュニティは新参者を非常に温かく迎え入れており、Lean Zulipチャットグループには質問に答えてくれる人々が24時間体制で待機しています。そこであなたにお会いできることを楽しみにしていますし、あなたもすぐにそのような質問に答えられるようになり、Mathlibの開発に貢献できるようになると確信しています。

それでは、受諾することを選んだ場合のあなたのミッションです：飛び込み、演習問題を解き、質問を抱えてZulipを訪れ、そして楽しんでください。ただし警告しておきます：対話型定理証明は、数学および数学的推論について全く新しい方法で考えるようあなたに挑戦してきます。あなたの人生は二度と元には戻らないかもしれません。

    • 2. 基本事項（Basics）

    本章の目的は、Leanにおける数学的推論の基本、すなわち「計算の実行」「補題や定理の適用」「汎用的な構造についての推論」を学ぶことです。

    2.1. 計算（Calculating）

    私たちは通常、数学的な計算を行う際、それを証明として意識することはありません。しかし、Leanが要求するように計算の各ステップを正当化していくと、その結果として「計算の左辺と右辺が等しい」という証明が完成します。

    Leanでは、定理を述べることはゴール（すなわち、その定理を証明するというゴール）を述べることと同義です。Leanには、ゴールの等式の左辺を右辺で置き換えるための rw（rewrite）タクティクが用意されています。a、b、c が実数であるとき、mul_assoc a b c は等式 a * b * c = a * (b * c) であり、mul_comm a b は等式 a * b = b * a です。Leanには、このような事実を明示的に言及する必要性を一般になくしてくれる自動化機能が備わっていますが、ここでは説明の目的のためにこれらを使用します。Leanでは乗算は左結合であるため、mul_assoc の左辺は (a * b) * c と書くこともできます。しかし、Leanの記法上の規約に留意し、Leanがそうするように括弧を省略するのが一般に良いスタイルとされています。

    実際に rw を試してみましょう。

    example (a b c : ℝ) : a * b * c = b * (a * c) := by
  rw [mul_comm a b]
  rw [mul_assoc b a c]

    対応する例ファイルの先頭にある module および public import 行は、Mathlibから実数の理論と便利な自動化機能をインポートします。より正確には、module 行はMathlibから public とマークされた定義と定理のみをインポートするようにLeanに指示し、public キーワードは、このファイルをインポートするすべてのファイルにおいてそれらを公開し続けるようLeanに指示します。これらの詳細については今のところ無視して構いません。「import」コマンドは、Mathlibのどの部分を使用したいかをLeanに伝えるものである、という点を知っておくことが最も重要です。紙幅の都合上、本書ではこのような情報は一般に省略しています。

    変更を加えるとどうなるか、自由に試してみてください。VS Codeでは、ℝ 文字を \R または \real と入力できます。スペースキーまたはタブキーを押すまで、記号は表示されません。Leanファイルを読んでいるときに記号にカーソルを合わせると、その入力に使用できる構文がVS Codeに表示されます。利用可能なすべての省略形を確認したい場合は、Ctrl-Shift-P を押してから abbreviations と入力すると、Lean 4: Show Unicode Input Abbreviations コマンドにアクセスできます。お使いのキーボードにアクセスしやすいバックスラッシュがない場合は、lean4.input.leader 設定を変更することで先頭の文字を変更できます。

    タクティクによる証明の途中にカーソルがある場合、Leanは Lean Infoview ウィンドウに現在の証明の状態（proof state）を表示します。証明の各ステップを進めるにつれて、状態の変化を確認できます。Leanにおける典型的な証明の状態は、次のような見た目をしています：

    1 goal
x y : ℕ,
h₁ : Prime x,
h₂ : ¬Even x,
h₃ : y > x
⊢ y ≥ 4

    ⊢ で始まる行より前の行はコンテキスト（context）を表しており、現在有効なオブジェクトと仮定を示しています。この例では、それぞれが自然数である x と y という2つのオブジェクトが含まれています。また、h₁, h₂, h₃ とラベル付けされた3つの仮定も含まれています。Leanでは、コンテキスト内のすべてのものに識別子がラベル付けされます。これらの下付文字のラベルは h\1、h\2、h\3 と入力できますが、どの正当な識別子でも構いません。代わりに h1、h2、h3 を使っても良いですし、foo、bar、baz でも構いません。最後の行はゴール（goal）、すなわち証明すべき事実を表します。証明すべき事実に対して target という言葉を使い、コンテキストとターゲットの組み合わせに対して goal という言葉を使う人もいます。実用上、意図される意味は通常明確です。

    それぞれの場所で sorry をタクティク証明に置き換えながら、次の等式を証明してみてください。rw タクティクでは、左矢印（\l）を使用して等式を逆に適用することができます。例えば、rw [← mul_assoc a b c] は、現在のゴール内の a * (b * c) を a * b * c に置き換えます。左を向く矢印は、mul_assoc が提供する等式を右から左へ辿ることを指しており、ゴールの左側や右側とは何ら関係がないことに注意してください。

    example (a b c : ℝ) : c * b * a = b * (a * c) := by
  sorry

example (a b c : ℝ) : a * (b * c) = b * (a * c) := by
  sorry

    また、mul_assoc や mul_comm のような等式を引数なしで使用することもできます。この場合、書き換え（rewrite）タクティクは、最初に見つかったパターンを使用して、左辺とゴール内の式をマッチさせようと試みます。

    example (a b c : ℝ) : a * b * c = b * c * a := by
  rw [mul_assoc]
  rw [mul_comm]

    部分的な情報を与えることもできます。例えば、mul_comm a は a * ? の形の任意のパターンにマッチし、? * a に書き換えます。引数を一切与えずに1番目の例を解き、引数を1つだけ与えて2番目の例を解いてみてください。

    example (a b c : ℝ) : a * (b * c) = b * (c * a) := by
  sorry

example (a b c : ℝ) : a * (b * c) = b * (a * c) := by
  sorry

    ローカルコンテキストにある事実と一緒に rw を使用することもできます。

    example (a b c d e f : ℝ) (h : a * b = c * d) (h' : e = f) : a * (b * e) = c * (d * f) := by
  rw [h']
  rw [← mul_assoc]
  rw [h]
  rw [mul_assoc]

    2番目の例では定理 sub_self を使用して、次を解いてみてください：

    example (a b c d e f : ℝ) (h : b * c = e * f) : a * b * c * d = a * e * f * d := by
  sorry

example (a b c d : ℝ) (hyp : c = b * a - d) (hyp' : d = a * b) : c = 0 := by
  sorry

    角括弧の中にカンマで区切って関連する等式を並べることで、複数の書き換えコマンドをひとつのコマンドで実行できます。

    example (a b c d e f : ℝ) (h : a * b = c * d) (h' : e = f) : a * (b * e) = c * (d * f) := by
  rw [h', ← mul_assoc, h, mul_assoc]

    書き換えのリスト内のカンマの後にカーソルを置くことで、段階的な進捗を確認することができます。

    もう一つのテクニックとして、例や定理の外側で変数を一度だけ宣言するという方法があります。これにより、Leanはそれらを自動的に含めてくれます。

    variable (a b c d e f : ℝ)

example (h : a * b = c * d) (h' : e = f) : a * (b * e) = c * (d * f) := by
  rw [h', ← mul_assoc, h, mul_assoc]

    上記証明の開始時点におけるタクティク状態を検査すると、Leanが実際にすべての変数を含めていることが分かります。宣言の有効範囲は、section ... end ブロック内に置くことで区切ることができます。最後に、導入部で触れたように、Leanには式の型を決定するコマンドが用意されていることを思い出してください：

    section
variable (a b c : ℝ)

#check a
#check a + b
#check (a : ℝ)
#check mul_comm a b
#check (mul_comm a b : a * b = b * a)
#check mul_assoc c a b
#check mul_comm a
#check mul_comm
end

    #check コマンドは、オブジェクトと事実の両方に対して機能します。#check a というコマンドに対して、Leanは a が ℝ 型であると報告します。#check mul_comm a b というコマンドに対して、Leanは mul_comm a b が a * b = b * a という事実の証明であると報告します。コマンド #check (a : ℝ) は、a の型が ℝ であるという私たちの期待を表明するものであり、そうでない場合、Leanはエラーを発生させます。最後の3つの #check コマンドの出力については後ほど説明しますが、その間にそれらを確認したり、ご自身の #check コマンドをいくつか試したりしてみてください。

    さらにいくつかの例を試してみましょう。定理 two_mul a は 2 * a = a + a であることを述べます。定理 add_mul および mul_add は乗算の加算に対する分配律を表し、定理 add_assoc は加算の結合律を表します。正確な記述を確認するには、#check コマンドを使用してください。

    example : (a + b) * (a + b) = a * a + 2 * (a * b) + b * b := by
  rw [mul_add, add_mul, add_mul]
  rw [← add_assoc, add_assoc (a * a)]
  rw [mul_comm b a, ← two_mul]

    エディタでステップ実行して何が起きているかを把握することは可能ですが、これ単体では読むのが困難です。Leanには、calc キーワードを使用してこのような証明をより構造化して書く方法が用意されています。

    example : (a + b) * (a + b) = a * a + 2 * (a * b) + b * b :=
  calc
    (a + b) * (a + b) = a * a + b * a + (a * b + b * b) := by
      rw [mul_add, add_mul, add_mul]
    _ = a * a + (b * a + a * b) + b * b := by
      rw [← add_assoc, add_assoc (a * a)]
    _ = a * a + 2 * (a * b) + b * b := by
      rw [mul_comm b a, ← two_mul]

    証明が by で始まっていないことに注意してください。calc で始まる式は証明項（proof term）です。calc 式はタクティク証明の中でも使用できますが、Leanはそれを「結果として得られる証明項を使用してゴールを解く」という指示として解釈します。calc の構文は厳格です。アンダースコアと正当化（justification）は上記で示されたフォーマットに従う必要があります。Leanは、タクティクのブロックや calc ブロックがどこで始まりどこで終わるかなどの判定にインデントを利用します。上の証明のインデントを変更して何が起きるか試してみてください。

    calc 証明を書く一つの方法として、正当化のために sorry タクティクを使用してまず全体の輪郭を描き、Leanがそれらを法として式を受け入れることを確認してから、タクティクを使って個々のステップを正当化するというやり方があります。

    example : (a + b) * (a + b) = a * a + 2 * (a * b) + b * b :=
  calc
    (a + b) * (a + b) = a * a + b * a + (a * b + b * b) := by
      sorry
    _ = a * a + (b * a + a * b) + b * b := by
      sorry
    _ = a * a + 2 * (a * b) + b * b := by
      sorry

    純粋な rw 証明と、より構造化された calc 証明の両方を使って、次の等式を証明してみてください：
    以下の演習問題は少し挑戦しがいがあります。下部に挙げられている定理を使用できます（すべてを使う必要はありません）。

    example (a b : ℝ) : (a + b) * (a - b) = a ^ 2 - b ^ 2 := by
  sorry

#check pow_two a
#check mul_sub a b c
#check add_mul a b c
#check add_sub a b c
#check sub_sub a b c
#check sub_add a b c
#check add_zero a
#check sub_zero a
#check sub_self a

    コンテキスト内の仮定に対して書き換えを行うこともできます。例えば、rw [mul_comm a b] at hyp は、仮定 hyp の中の a * b を b * a に置き換えます。

    variable (a b c d : ℝ)

example (hyp : c = d * a + b) (hyp' : b = a * d) : c = 2 * a * d := by
  rw [hyp'] at hyp
  rw [mul_comm d a] at hyp
  rw [← two_mul (a * d)] at hyp
  rw [← mul_assoc 2 a d] at hyp
  exact hyp

    最後のステップでは、その時点で hyp がゴールと完全に一致するため、exact タクティクは hyp を用いてゴールを解くことができます。

    本節の締めくくりとして、Mathlibには ring タクティクという便利な自動化機能が備わっていることに触れておきます。これは、ローカルな仮定を使用せず、もっぱら環の公理から従う限り、任意の可換環における等式を証明するように設計されています。

    example : c * b * a = b * (a * c) := by
  ring

example : (a + b) * (a + b) = a * a + 2 * (a * b) + b * b := by
  ring

example : (a + b) * (a - b) = a ^ 2 - b ^ 2 := by
  ring

example (hyp : c = d * a + b) (hyp' : b = a * d) : c = 2 * a * d := by
  rw [hyp, hyp']
  ring

    ring タクティクは、Mathlib.Basic.Real.Basic を public importするときに間接的にインポートされますが、次のセクションで見るとおり、実数以外の構造に関する計算にも使用できます。これはコマンド import Mathlib.Tactic で明示的にインポートすることもできます。他の一般的な種類の代数構造に対しても、同様のタクティクが存在することが分かります。

    rw のバリエーションとして nth_rw と呼ばれるものがあり、これを使うとゴール内の式の特定の部分インスタンスのみを置き換えることができます。可能なマッチは1から始まる番号で列挙されるため、次の例では、nth_rw 2 [h] は a + b の2番目の出現を c に置き換えます。

    example (a b c : ℕ) (h : a + b = c) : (a + b) * (a + b) = a * c + b * c := by
  nth_rw 2 [h]
  rw [add_mul]

    2.2. 代数構造における等式の証明（Proving Identities in Algebraic Structures）

    数学的に、環（ring）は、オブジェクトの集合 R、演算 + および *、定数 0 および 1、そして演算 - からなり、以下を満たします：

    • + を伴う R はアーベル群であり、0 が加法の単位元、加法逆元がマイナスである。
    • 乗算は単位元 1 を持って結合的であり、乗算は加算に対して分配する。

    Leanでは、オブジェクトの集合は型 R として表現されます。環の公理は以下の通りです：

    variable (R : Type*) [Ring R]

#check (add_assoc : ∀ a b c : R, a + b + c = a + (b + c))
#check (add_comm : ∀ a b : R, a + b = b + a)
#check (zero_add : ∀ a : R, 0 + a = a)
#check (neg_add_cancel : ∀ a : R, -a + a = 0)
#check (mul_assoc : ∀ a b c : R, a * b * c = a * (b * c))
#check (mul_one : ∀ a : R, a * 1 = a)
#check (one_mul : ∀ a : R, 1 * a = a)
#check (mul_add : ∀ a b c : R, a * (b + c) = a * b + a * c)
#check (add_mul : ∀ a b c : R, (a + b) * c = a * c + b * c)

    最初の行にある角括弧については後ほど詳しく学びますが、現時点では、この宣言によって型 R と、R 上の環構造が得られる、と言えば十分です。これによりLeanでは、R の元に対して一般的な環の表記法を使用できるようになり、環に関する定理のライブラリを利用できるようになります。

    定理の名のいくつかは見覚えがあるはずです：それらはまさに前節で実数の計算に使用したものです。Leanは、自然数や整数のような具体的な数学的構造についての証明だけでなく、環のように公理的に特徴づけられる抽象的な構造についての証明にも優れています。さらに、Leanは抽象的構造と具体的構造の両方に関する汎用的な推論（generic reasoning）をサポートしており、適切なインスタンスを認識するように訓練することができます。したがって、環に関する任意の定理を、整数 ℤ、有理数 ℚ、複素数 ℂ といった具体的な環に適用することができます。また、順序環や体など、環を拡張する抽象構造の任意のインスタンスにも適用できます。

    ただし、実数のすべての重要な性質が任意の環で成り立つわけではありません。例えば、実数における乗算は可換ですが、それは一般には成り立ちません。線形代数のコースを受講したことがある方であれば、任意の環において、実数の n 次正方行列全体が通常は可換性が成り立たない環をなすことが分かるでしょう。実際、R を可換環（commutative ring）として宣言すれば、ℝ を R に置き換えても前節のすべての定理がそのまま成り立ちます。

    variable (R : Type*) [CommRing R]
variable (a b c d : R)

example : c * b * a = b * (a * c) := by ring
example : (a + b) * (a + b) = a * a + 2 * (a * b) + b * b := by ring
example : (a + b) * (a - b) = a ^ 2 - b ^ 2 := by ring
example (hyp : c = d * a + b) (hyp' : b = a * d) : c = 2 * a * d := by
  rw [hyp, hyp']
  ring

    残りの証明がそのまま成り立つことの確認は読者の皆様にお任せします。証明が by ring や by linarith、by sorry のように短い場合、それを by と同じ行に置くことが一般的であり（かつ許容されており）、推奨されます。良い証明記述のスタイルは、簡潔性と可読性のバランスを取るべきです。

    本節の目的は、前節で培ったスキルを強化し、それを環に関する公理的推論に応用することです。上記の公理から始めて、他の事実を導出します。私たちが証明する事実のほとんどはすでにMathlibに含まれています。ライブラリの内容や命名規則を学べるよう、証明するバージョンには同じ名前を付けます。

    Leanにはプログラミング言語で使用されるものと同様の組織化の仕組みが用意されています：定義や定理 foo が名前空間 bar 内で導入されるとき、その完全な名前は bar.foo になります。その後のコマンド open bar は名前空間を開き、より短い名前 foo を使用できるようにします。名前の衝突によるエラーを避けるため、次の例では、ライブラリの定理の私たちのバージョンを MyRing という新しい名前空間に入れます。

    次の例は、他の公理から従うため、add_zero や add_neg_cancel を環の公理として必要としないことを示しています。

    namespace MyRing
variable {R : Type*} [Ring R]

theorem add_zero (a : R) : a + 0 = a := by rw [add_comm, zero_add]

theorem add_neg_cancel (a : R) : a + -a = 0 := by rw [add_comm, neg_add_cancel]

#check MyRing.add_zero
#check add_zero

end MyRing

    結果として、ライブラリ内の定理を一時的に再証明し、その後はライブラリのバージョンを使い続けることができます。しかし、ズルをしてはいけません！続く演習問題では、このセクションの前半で証明した環に関する一般的な事実のみを使用するように注意してください。

    （注意深く見ておられる方であれば、(R : Type*) の丸括弧が {R : Type*} の波括弧に変更されていることに気づいたかもしれません。これは R を暗黙の引数（implicit argument）として宣言するものです。これが何を意味するかは後ほど説明しますが、現時点では気にしないでください。）

    ここに有用な定理があります：

    theorem neg_add_cancel_left (a b : R) : -a + (a + b) = b := by
  rw [← add_assoc, neg_add_cancel, zero_add]

    対となるバージョンを証明してください：

    theorem add_neg_cancel_right (a b : R) : a + b + -b = a := by
  sorry

    これらを使用して次を証明してください：

    theorem add_left_cancel {a b c : R} (h : a + b = a + c) : b = c := by
  sorry

theorem add_right_cancel {a b c : R} (h : a + b = c + b) : a = c := by
  sorry

    十分な計画を立てれば、それぞれ3回の書き換えで実行できます。

    それでは、波括弧の使用法について説明します。コンテキスト内に a、b、c があり、さらに仮定 h : a + b = a + c があって、結論 b = c を導き出したいという状況を想像してください。Leanでは、オブジェクトに適用するのと全く同じ方法で、定理を仮定や事実にも適用できるため、add_left_cancel a b c h が事実 b = c の証明であると思われるかもしれません。しかし、a、b、c を明示的に記述することは冗長であることに注意してください。なぜなら、仮定 h がそれらが念頭に置いているオブジェクトであることを明確にしているからです。この場合、数文字多くタイピングすることは大きな負担ではありませんが、より複雑な式に add_left_cancel を適用したい場合、それらを書き下すのは面倒です。このような場合に備えて、Leanでは引数を暗黙（implicit）としてマークすることができます。これは、それらを省略し、後の引数や仮定などの他の手段から推論させるべきであることを意味します。{a b c : R} の波括弧はまさにそれを行います。したがって、上記の定理の記述が与えられたとき、正しい式は単に add_left_cancel h となります。

    例として、a * 0 = 0 が環の公理から従うことを示しましょう。

    theorem mul_zero (a : R) : a * 0 = 0 := by
  have h : a * 0 + a * 0 = a * 0 + 0 := by
    rw [← mul_add, add_zero, add_zero]
  rw [add_left_cancel h]

    新しいテクニックを使用しました！ステップ実行すると、何が起きているか分かります。have タクティクは、元のゴールと同じコンテキストで、新しいゴール a * 0 + a * 0 = a * 0 + 0 を導入します。次の行がインデントされているという事実は、Leanがこの新しいゴールを証明するためのタクティクのブロックを期待していることを示しています。したがって、インデントはモジュール式の証明スタイルを促進します：インデントされたサブ証明が have によって導入されたゴールを確立します。その後、新しい仮定 h が追加された点を除いて、元のゴールの証明に戻ります：それを証明したため、自由にそれを使用できるようになります。この時点で、ゴールはまさに add_left_cancel h の結果となります。

    apply add_left_cancel h または exact add_left_cancel h で証明を締めくくることも同様に可能です。exact タクティクは、新しいゴールを一切作成せずに、現在のゴールを完全に証明する証明項を引数として取ります。apply タクティクはその変種であり、その引数は必ずしも完全な証明である必要はありません。足りない部分はLeanによって自動的に推論されるか、証明すべき新しいゴールになります。exact タクティクは、apply よりも厳密に能力が低いため技術的には冗長ですが、人間にとって証明スクリプトをわずかに分かりやすくし、ライブラリが発展したときの保守を容易にします。

    乗算は可換であるとは仮定されていないため、次の定理にもいくらかの作業が必要です。

    theorem zero_mul (a : R) : 0 * a = 0 := by
  sorry

    ここまでくれば、a = b が b = a を意味する補題 Eq.symm と共に、このセクションで確立した環に関する事実のみを使用して、次の演習におけるそれぞれの sorry を証明に置き換えることができるはずです。

    theorem neg_eq_of_add_eq_zero {a b : R} (h : a + b = 0) : -a = b := by
  sorry

theorem eq_neg_of_add_eq_zero {a b : R} (h : a + b = 0) : a = -b := by
  sorry

theorem neg_zero : (-0 : R) = 0 := by
  apply neg_eq_of_add_eq_zero
  rw [add_zero]

theorem neg_neg (a : R) : - -a = a := by
  sorry

    3番目の定理では、0 の代わりに注釈 (-0 : R) を使用する必要がありました。なぜなら、R を指定しない場合、私たちがどの 0 を念頭に置いているかをLeanが推論することは不可能であり、デフォルトでは自然数として解釈されてしまうからです。

    Leanでは、環における減算は、加法逆元の加算と証明可能に等しいです。

    example (a b : R) : a - b = a + -b :=
  sub_eq_add_neg a b

    実数上では、それはそのように定義されています：

    example (a b : ℝ) : a - b = a + -b :=
  rfl

example (a b : ℝ) : a - b = a + -b := by
  rfl

    証明項 rfl は「反射律（reflexivity）」の略です。これを a - b = a + -b の証明として提示すると、Leanは定義を展開し、両辺が同一であることを認識するよう強いられます。rfl タクティクも同様のことを行います。これはLeanの基盤となるロジックにおける定義的等式（definitional equality）として知られるもののインスタンスです。これは、sub_eq_add_neg で書き換えて a - b = a + -b を置き換えることができるだけでなく、いくつかの文脈（実数を扱う場合など）では、等式の両辺を互換的に使用できることを意味します。例えば、前節の定理 self_sub を証明するのに十分な情報が揃いました：

    theorem self_sub (a : R) : a - a = 0 := by
  sorry

    rw を使ってこれを証明できることを示しつつ、任意の環 R を実数に置き換えた場合には、apply または exact のいずれかを使って証明できることも示してください。

    Leanは、任意の環において 1 + 1 = 2 が成り立つことを知っています。少しの労力で、それを利用して前節の定理 two_mul を証明することができます：

    example : 1 + 1 = (2 : R) := by
  norm_num

theorem two_mul (a : R) : 2 * a = a + a := by
  sorry

    本節の締めくくりとして、上記で確立した加算とマイナスに関する事実の一部は、環の公理のフルパワーや、加算の可換性さえも必要としないことに触れておきます。より弱い概念である群（group）は、次のように公理化できます：

    variable (A : Type*) [AddGroup A]

#check (add_assoc : ∀ a b c : A, a + b + c = a + (b + c))
#check (zero_add : ∀ a : A, 0 + a = a)
#check (neg_add_cancel : ∀ a : A, -a + a = 0)

    群演算が可換である場合は加法記法を使用するのが慣習であり、そうでない場合は乗法記法を使用します。そのため、Leanは加法バージョンと同様に乗法バージョン（およびそのアーベル版である AddCommGroup と CommGroup）も定義しています。

    variable {G : Type*} [Group G]

#check (mul_assoc : ∀ a b c : G, a * b * c = a * (b * c))
#check (one_mul : ∀ a : G, 1 * a = a)
#check (inv_mul_cancel : ∀ a : G, a⁻¹ * a = 1)

    もし自信があれば、これらの公理のみを使用して、群に関する次の事実を証明してみてください。その過程で、いくつかのヘルパー補題を証明する必要があります。このセクションで私たちが実行した証明は、いくつかのヒントを提供しています。

    theorem mul_inv_cancel (a : G) : a * a⁻¹ = 1 := by
  sorry

theorem mul_one (a : G) : a * 1 = a := by
  sorry

theorem mul_inv_rev (a b : G) : (a * b)⁻¹ = b⁻¹ * a⁻¹ := by
  sorry

    それらの補題を明示的に呼び出すのは面倒なため、Mathlibにはほとんどの用途をカバーするために ring に似たタクティクが用意されています：非可換乗法群に対しては group、アーベル加法群に対しては abel、非可換環に対しては noncomm_ring があります。代数構造が Ring と CommRing と呼ばれる一方で、タクティクが noncomm_ring と ring と名付けられているのは奇妙に見えるかもしれません。これは歴史的な理由もありますが、可換環を扱うタクティクの方が頻繁に使用されるため、より短い名前を使用する利便性のためでもあります。

    2.3. 定理と補題の使用（Using Theorems and Lemmas）

    書き換えは等式の証明には最適ですが、他の種類の定理についてはどうでしょうか？例えば、 a ≤ b であるときはいつでも f(a) ≤ f(b) が成り立つというような不等式をどのように証明すればよいでしょうか？定理を引数や仮定に適用できること、そして apply や exact タクティクを用いてゴールを解けることはすでに見てきました。本節では、これらのツールを大いに活用します。

    ライブラリの定理 le_refl と le_trans を考えてみましょう：

    #check (le_refl : ∀ a : ℝ, a ≤ a)
#check (le_trans : a ≤ b → b ≤ c → a ≤ c)

    3.1節 で詳しく説明するように、le_trans の記述における暗黙の括弧は右結合であるため、これは a ≤ b → (b ≤ c → a ≤ c) として解釈されるべきです。ライブラリの設計者は、Leanがそれらを明示的に提供させてしまわないように（後で説明するように、どうしても主張する場合を除き）、le_trans の引数 a、b、c を暗黙に設定しています。むしろ、それらが使用されるコンテキストから推論されることを期待しています。例えば、仮定 h : a ≤ b と h' : b ≤ c がコンテキストにある場合、以下のすべてが機能します：

    variable (h : a ≤ b) (h' : b ≤ c)

#check (le_refl : ∀ a : Real, a ≤ a)
#check (le_refl a : a ≤ a)
#check (le_trans : a ≤ b → b ≤ c → a ≤ c)
#check (le_trans h : b ≤ c → a ≤ c)
#check (le_trans h h' : a ≤ c)

    apply タクティクは、一般のステートメントや含意の証明を受け取り、結論を現在のゴールにマッチさせようとし、もしあれば仮定を新しいゴールとして残します。与えられた証明が（定義的等式を法として）ゴールと完全に一致する場合、apply の代わりに exact タクティクを使用できます。したがって、これらはすべて機能します：

    example (x y z : ℝ) (h₀ : x ≤ y) (h₁ : y ≤ z) : x ≤ z := by
  apply le_trans
  · apply h₀
  · apply h₁

example (x y z : ℝ) (h₀ : x ≤ y) (h₁ : y ≤ z) : x ≤ z := by
  apply le_trans h₀
  apply h₁

example (x y z : ℝ) (h₀ : x ≤ y) (h₁ : y ≤ z) : x ≤ z :=
  le_trans h₀ h₁

example (x : ℝ) : x ≤ x := by
  apply le_refl

example (x : ℝ) : x ≤ x :=
  le_refl x

    最初の例では、le_trans を適用すると2つのゴールが生成され、それぞれの証明がどこから始まるかを示すために中黒（ドット）を使用しています。ドットは省略可能ですが、ゴールをフォーカス（focus）する役割を果たします：ドットによって導入されたブロック内では1つのゴールのみが見えており、ブロックが終了する前にそれを完了しなければなりません。ここでは、別のドットで新しいブロックを開始することで最初のブロックを終了しています。インデントを減らしても同様に機能します。3番目の例と最後の例では、タクティクモードに入ることを完全に回避しています：le_trans h₀ h₁ と le_refl x は私たちが必要とする証明項です。

    ライブラリの定理をもう少し挙げます：

    #check (le_refl : ∀ a, a ≤ a)
#check (le_trans : a ≤ b → b ≤ c → a ≤ c)
#check (lt_of_le_of_lt : a ≤ b → b < c → a < c)
#check (lt_of_lt_of_le : a < b → b ≤ c → a < c)
#check (lt_trans : a < b → b < c → a < c)

    これらを apply や exact と一緒に使用して、次を証明してください：

    example (h₀ : a ≤ b) (h₁ : b < c) (h₂ : c ≤ d) (h₃ : d < e) : a < e := by
  sorry

    実際、Leanにはこの種の処理を自動で行うタクティクがあります：

    example (h₀ : a ≤ b) (h₁ : b < c) (h₂ : c ≤ d) (h₃ : d < e) : a < e := by
  linarith

    linarith タクティクは線形算術（linear arithmetic）を処理するように設計されています。

    example (h : 2 * a ≤ 3 * b) (h' : 1 ≤ a) (h'' : d = 2) : d + a ≤ 5 * b := by
  linarith

    コンテキスト内の等式や不等式に加えて、linarith は引数として渡す追加の不等式も使用します。次の例では、後で説明するように、exp_le_exp.mpr h' は exp b ≤ exp c の証明です。Leanでは、事実や定理 h を引数 x に適用した結果を表すのに h x と書くのと全く同じ方法で、関数 f を引数 x に適用したことを表すために f x と書くことに注意してください。括弧が必要なのは、f (x + y) のような複合引数の場合のみです。括弧がない場合、f x + y は (f x) + y としてパースされます。

    example (h : 1 ≤ a) (h' : b ≤ c) : 2 + a + exp b ≤ 3 * a + exp c := by
  linarith [exp_le_exp.mpr h']

    実数上の不等式を確立するために使用できるライブラリの定理を他にもいくつか示します。

    #check (exp_le_exp : exp a ≤ exp b ↔ a ≤ b)
#check (exp_lt_exp : exp a < exp b ↔ a < b)
#check (log_le_log : 0 < a → a ≤ b → log a ≤ log b)
#check (log_lt_log : 0 < a → a < b → log a < log b)
#check (add_le_add : a ≤ b → c ≤ d → a + c ≤ b + d)
#check (add_le_add_right : a ≤ b → ∀ c, c + a ≤ c + b)
#check (add_le_add_left : a ≤ b → ∀ c, a + c ≤ b + c)
#check (add_lt_add_of_le_of_lt : a ≤ b → c < d → a + c < b + d)
#check (add_lt_add_of_lt_of_le : a < b → c ≤ d → a + c < b + d)
#check (add_lt_add_right : a < b → ∀ c, c + a < c + b)
#check (add_lt_add_left : a < b → ∀ c, a + c < b + c)
#check (add_nonneg : 0 ≤ a → 0 ≤ b → 0 ≤ a + b)
#check (add_pos : 0 < a → 0 < b → 0 < a + b)
#check (add_pos_of_pos_of_nonneg : 0 < a → 0 ≤ b → 0 < a + b)
#check (exp_pos : ∀ a, 0 < exp a)

    定理の中には、exp_le_exp や exp_lt_exp のように「必要十分条件」を表す双方向含意（bi-implication）を使用するものがあります。（VS Codeでは \lr または \iff で入力できます）。この結合子については次章で詳しく説明します。このような定理は、ゴールを等価なものに書き換えるために rw と共に使用できます：

    example (h : a ≤ b) : exp a ≤ exp b := by
  rw [exp_le_exp]
  exact h

    しかし、本節では、h : A ↔ B がそのような同値性である場合、h.mp が正方向 A → B を確立し、h.mpr が逆方向 B → A を確立するという事実を利用します。ここで、mp は「モデウス・ポネンス（modus ponens）」の略であり、mpr は「モデウス・ポネンス・リバース（modus ponens reverse）」の略です。お好みであれば、h.mp や h.mpr の代わりに h.1 や h.2 を使用することもできます。したがって、次の証明が機能します：

    example (h₀ : a ≤ b) (h₁ : c < d) : a + exp c + e < b + exp d + e := by
  apply add_lt_add_of_lt_of_le
  · apply add_lt_add_of_le_of_lt h₀
    apply exp_lt_exp.mpr h₁
  apply le_refl

    最初の行 apply add_lt_add_of_lt_of_le は2つのゴールを生成し、ここでも1つ目の証明を2つ目の証明から切り離すためにドットを使用しています。

    ご自身で次の例を試してみてください。中央の例は、具体的な数値のゴールを解くために norm_num タクティクを使用できることを示しています。

    example (h₀ : d ≤ e) : c + exp (a + d) ≤ c + exp (a + e) := by sorry

example : (0 : ℝ) < 1 := by norm_num

example (h : a ≤ b) : log (1 + exp a) ≤ log (1 + exp b) := by
  have h₀ : 0 < 1 + exp a := by sorry
  apply log_le_log h₀
  sorry

    これらの例から、必要なライブラリの定理を見つけられることが形式化の重要な部分を占めていることは明らかです。次のような多くの戦略を利用できます：

    • GitHubリポジトリでMathlibを閲覧する。
    • MathlibのウェブページのAPIドキュメントを使用する。
    • パターンによってLeanおよびMathlibの定義や定理を検索するために Loogle を使用する。
    • Mathlibの命名規則とエディタでのCtrl-space補完に頼って定理名を推測する。Leanでは、A_of_B_of_C と名付けられた定理は、形式 B と C の仮定から形式 A の何かを確立します。ここで A、B、C はゴールの読み上げ方を近似したものです。したがって、x + y ≤ ... のようなものを確立する定理はおそらく add_le で始まります。add_le と入力してCtrl-spaceを押すと、役立つ選択肢がいくつか表示されます。なお、Ctrl-spaceを2回押すと、利用可能な補完に関するより多くの情報が表示されます。
    • VS Codeで既存の定理名を右クリックすると、その定理が定義されているファイルへジャンプするオプション付きのメニューが表示され、その近くで類似の定理を見つけることができる。
    • ライブラリから関連する定理を見つけようと試みる apply? タクティクを使用する。
    example : 0 ≤ a ^ 2 := by
  -- apply?
  exact sq_nonneg a

    この例で apply? を試すには、exact コマンドを削除し、前の行のコメントアウトを外してください。これらのテクニックを使って、次の例を解くために必要なものを見つけられるか試してみてください：

    example (h : a ≤ b) : c - exp b ≤ c - exp a := by
  sorry

    同じテクニックを使用して、apply? の代わりに linarith でも同様に処理を完了できることを確認してください。

    不等式の別の例を示します：

    example : 2*a*b ≤ a^2 + b^2 := by
  have h : 0 ≤ a^2 - 2*a*b + b^2
  calc
    a^2 - 2*a*b + b^2 = (a - b)^2 := by ring
    _ ≥ 0 := by apply pow_two_nonneg
  calc
    2*a*b = 2*a*b + 0 := by ring
    _ ≤ 2*a*b + (a^2 - 2*a*b + b^2) := add_le_add (le_refl _) h
    _ = a^2 + b^2 := by ring

    Mathlibは * や ^ のような二項演算子の周囲にスペースを置く傾向がありますが、この例では、より圧縮されたフォーマットにより可読性が向上しています。いくつか注目すべき点があります。第一に、式 s ≥ t は t ≤ s と定義上同値です。原則として、これはそれらを互換的に使用できるべきであることを意味します。しかし、Leanの自動化の中にはこの同値性を認識しないものもあるため、Mathlibは ≥ よりも ≤ を好む傾向があります。第二に、私たちは ring タクティクを多用しました。これは大変な時間の節約になります！最後に、2つ目の calc 証明の2行目で、by exact add_le_add (le_refl _) h と書く代わりに、単に証明項 add_le_add (le_refl _) h と書くことができることに注目してください。

    実際、上記の証明における唯一の工夫は仮定 h を見つけ出すことです。それを手に入れさえすれば、2つ目の計算は線形算術のみを含んでおり、linarith がそれを処理できます：

    example : 2*a*b ≤ a^2 + b^2 := by
  have h : 0 ≤ a^2 - 2*a*b + b^2
  calc
    a^2
